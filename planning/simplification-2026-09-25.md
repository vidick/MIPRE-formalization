# Simplification survey, 2026-09-25

**Status: record only.** The maintainer chose (2026-09-25) to record the candidates and make no
source change beyond the one name collision in project-written code. Nothing below is
implemented; each entry is written so that an implementing PR can follow the trail. Tracking
issue: #225. The eleven area reports with the full evidence are in
[`simplification-2026-09-25/`](simplification-2026-09-25/), and the two machine-generated lists
(`dead-declarations.txt`, `unreferenced-attributed.txt`) are regenerated by
`scripts/lean-dead.py`. Counts are snapshots of `main` at `ea13614`; the newest note wins.

## 1. Method, and what was excluded as settled

The survey followed the `find-simplification` skill of `texra-ai/texra-lean-skills` (0.4.0):
grep proposes, elaboration decides; consumers are counted on the final name component, not the
full name; a declaration always references itself, so a count of zero is a matcher bug.

Two passes.

1. **Mechanical, compiler-backed.** `scripts/lean-dead.py` reads Lean's own reference index
   (`.lake/build/lib/lean/**/*.ilean`, format 5), in which every elaborated identifier use is
   recorded with its enclosing declaration. A declaration is dead when nothing outside its own
   body uses it, iterated to a fixpoint so that a definition whose only users were dead lemmas
   is dead too. Blueprint `\lean{}` tags (4,411 names) and the four axiom-guard files are
   consumers by policy. Instances and attribute-carrying lemmas are excluded: `simp` and
   instance resolution fire without an identifier, which the index cannot see. A first
   grep-based pass had found 545 dead declarations; the index confirmed 533 of them and found
   197 more that a homonym elsewhere had masked, which is why the script reads the index.
2. **Eleven read-only area surveys** by agents, one directory each (the two largest split in
   half), for the shapes consumer counting cannot see: duplicates, Mathlib and Foundations
   shadows, pass-throughs, sequel chains, special cases kept beside their general form,
   superseded routes. Evidence is `path:line` with the survivor named; compiler probes
   (`lean_run_code`, `lean_references`, `exact?`) where cheap. No file under `MIPRE/` was
   edited and no build was run to confirm any deletion: every "net lines" figure is an
   estimate from reading.

Excluded as settled: the four vendored trees (`Repetition/TenProofs`,
`Repetition/CommutingRepetition`, `LIDT/MIPStarRE`, `Orthonormalization/Orthogonalization`);
`MIPRE.lean` (a generated aggregator, not a consumer); the guard files; every blueprint-tagged
declaration (at most a "replace and redirect the tag" candidate, low priority); designs with a
recorded rationale in `planning/*.md` or a module docstring, which are challenged only with new
evidence and are listed under "retained on purpose" below.

Three things learned about the tools, worth more than any single find:

- **Lean 4.33 accepts two modules that export the same constant name.** Importing both raises
  no error or warning; the later import wins. The library built with two such collisions
  (below) only because the two copies were equivalent. `lean_name_collisions.py` of the skill
  finds them; nothing in the toolchain does.
- **Blueprint prose is not a consumer.** A `\texttt{MIPRE.LCS.SolutionGroup.…}` in the text of
  `def:solution-group` (`02_foundations.tex:375`) is what kept about 1,400 lines of `MIPRE/LCS/`
  out of the first grep pass; only `\lean{}` tags count, and the index-based script counts only
  those.
- **The dead-list numbers undercount.** Everything the index cannot see (538 attribute-carrying
  declarations with no recorded usage at all) needs a build with the attribute or the
  declaration removed to rule on; and the agents' cluster finds (a whole route kept alive by
  its own last rung) sit largely inside the 750 but are not visible as such in a flat list.
